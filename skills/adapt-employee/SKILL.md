# /adapt-employee — Адаптация агента под клиентский офис

Демиург смотрит на агента которого пользователь переносит в клиентский офис и проверяет: **звучит ли он как живой человек** для клиента + **подключён ли он к офису правильно**. Выдаёт список правок-предложений с severity, ждёт одобрение, применяет — **через `overrides.md` агента, не через правку `core.md`**.

**Принцип:** клиент не должен видеть техническую кухню. Никаких «📚 Прочитал память», имён файлов вслух, slash-команд в речи.

**Архитектурный принцип (классификация находок):**

Каждая находка имеет тип:

- **`SYSTEM-BUG`** — плохой дизайн в исходнике, ломает любого клиента одинаково (например «📚 Прочитал память» в Pre-flight, методологические термины в речи клиенту). Чинится в **`core.md` мастер-пака**, бампается версия пака, ученики получают через `/update-office`. Один раз — навсегда.
- **`CLIENT-SPECIFIC`** — у конкретного клиента специфика (тон «вы»/«ты», ниша медицина без обещаний, запреты на мат, ценовые коридоры). Чинится в **`overrides.md` клиента**, в раздел `## Адаптация (auto)` с маркером `<!-- adapt-employee {date} -->` чтобы отделить от пользовательских правок руками.

При классификации скилл смотрит на природу проблемы:
- «У ВСЕХ клиентов это будет звучать криво?» → SYSTEM-BUG
- «У этого конкретного клиента специфика?» → CLIENT-SPECIFIC

Если SYSTEM-BUG — скилл предупреждает: «это требует обновить публичный пак, бампнуть версию, push в GitHub». Сам push скилл не делает — это решение пользователя.

## Когда запускать

| Триггер | Действие |
|---------|----------|
| «Адаптируй <агента> под клиента <имя>» | Запускай |
| «Перенеси <агента> в офис <клиент>» | Запускай |
| «Подготовь <агента> к переносу» | Запускай (без целевого офиса — только Voice/UX часть) |
| Только что скопирован пак агента в клиентский офис | Запускай |
| Создание нового агента с нуля | НЕ нужен — это `/build` |
| Общий аудит готового офиса | НЕ нужен — это `/office-cleaner (Рита)` |
| Правка ≤30 строк в одном файле | НЕ нужен — просто правь |

## Вход

```
/adapt-employee <agent-slug> <client-office-path>

Примеры:
  /adapt-employee alex-marketer ./client-office-template/
  /adapt-employee alex-marketer <путь-до-офиса-клиента>/
  /adapt-employee atlas /path/to/client/office

Опционально:
  --voice-only      — только Этап 1 (Voice/UX), без Wiring
  --wiring-only     — только Этап 2 (Wiring), без Voice
```

**Если параметры не переданы** — Демиург спрашивает у пользователя одной фразой: «какого агента и в чей офис?». Без многоэтапного INTAKE — это понятно из контекста.

**Что считается «клиентским офисом»:**
- Папка с подпапкой `office/agents/<agent-slug>/` — стандартная структура
- ИЛИ папка с подпапкой `_agent-packs/<agent-slug>/` — пак готовый к установке (тогда работаем с паком, не с установленным агентом)

## Process (4 фазы)

### Фаза 0: Pre-flight

Перед любым ответом:

```bash
AGENT="<agent-slug>"
CLIENT_OFFICE="<client-office-path>"

# Базовые проверки
[ -d "$CLIENT_OFFICE" ] || { echo "STOP: офис не найден: $CLIENT_OFFICE"; exit 1; }

# Найти где живёт агент в целевом офисе (установлен или в паке)
if   [ -d "$CLIENT_OFFICE/office/agents/$AGENT" ]; then
  TARGET="$CLIENT_OFFICE/office/agents/$AGENT"
  TARGET_KIND="installed"
elif [ -d "$CLIENT_OFFICE/_agent-packs/$AGENT" ]; then
  TARGET="$CLIENT_OFFICE/_agent-packs/$AGENT"
  TARGET_KIND="pack"
else
  echo "STOP: агента $AGENT нет в $CLIENT_OFFICE/office/agents/ или _agent-packs/"
  echo "Скопируй пак сначала, потом запусти скилл повторно."
  exit 1
fi
```

**Прочитать у цели**:
- `$TARGET/CLAUDE.md`, `$TARGET/core.md`, `$TARGET/soul.md`, `$TARGET/overrides.md`
- `$TARGET/skills/*/SKILL.md` (все привязанные скиллы — могут быть и в `$CLIENT_OFFICE/.claude/skills/$AGENT-*/`)
- `$TARGET/knowledge/INDEX.md` (если есть)
- `$TARGET/agent-state.md`, `$TARGET/memory.md`, `$TARGET/failures.md`

**Прочитать клиентский контекст**:
- `$CLIENT_OFFICE/CLAUDE.md` — корневой (главный Claude в чате)
- `$CLIENT_OFFICE/office/AGENTS.md` — карта команды
- `$CLIENT_OFFICE/office/agents/director/core.md` (если есть)
- `$CLIENT_OFFICE/office/client-profile.md` (для дамми-диалога)
- Список существующих агентов: `ls $CLIENT_OFFICE/office/agents/`

**Idempotency:** проверить `$TARGET/overrides.md` на маркер `<!-- adapted-by /adapt-employee {date} -->`. Если есть — спросить у пользователя: «вижу что агент уже был адаптирован {date}. Прогнать заново (искать новые проблемы поверх) или выйти?»

### Фаза 1: Voice/UX check

#### 1.1 Static проход

Загрузить таблицы из `references/forbidden-patterns.md`. Сканировать все тексты которые агент произносит клиенту. Это:

- Output Contract / примеры реплик в `core.md`
- Welcome / приветствия / характерные фразы в `soul.md`
- Формулировки вопросов клиенту в SKILL.md скиллов
- **Особо опасное место:** Input Contract / Pre-flight инструкции в `core.md`. Если там написано «обязательная служебная строка в первой реплике клиенту» с шаблоном — это автоматически BLOCKER (служебка попадает в речь).

Для каждого нарушения создаётся `finding`:

```yaml
phase: voice/static
severity: BLOCKER|MEDIUM|COSMETIC
file: <relative path>
line: <number>
pattern: <что нашли>
context: <окружающие 2-3 строки>
fix_proposal: <как пофиксить через overrides.md — какой блок добавить>
```

**LLM-судья дополняет regex.** После автоматики — Демиург перечитывает `core.md` целиком и ищет места что regex пропустил: тяжёлый канцелярит, методологические термины без объяснения, неживые приветствия. Это не строки кода, это **смысл** — поэтому без LLM-прохода никак.

#### 1.2 Behavioral проход (дамми-диалог)

⚠️ **Ограничение Claude Code:** subagent-в-subagent параллельно не работает. Поэтому используется **single-subagent two-roles**:

Запускается **один** subagent с промптом «играй обе роли по очереди — клиент и агент». Промпт-шаблон в `references/dummy-dialog-prompts.md`. Subagent ведёт 3-5 ходов:

```
[КЛИЕНТ]: Привет, расскажи кто ты и чем поможешь.
[АГЕНТ]: <реплика по конфигу core.md+soul.md+overrides.md>
[КЛИЕНТ]: <реакция на реплику, провокация по контексту>
[АГЕНТ]: ...
```

Сценарии **не зашиваются** — Демиург в промпте subagent'у даёт указание подбирать по контексту:
- Если в `core.md` есть Pre-flight гейты — провоцировать тяжёлым вопросом
- Если есть file ownership — клиент задаёт вопрос про данные, агент должен ответить **не упоминая файлы**
- Если есть методологические термины — клиент задаёт вопрос вынуждающий их использовать

После завершения диалога Демиург оценивает транскрипт по чек-листу из `references/dummy-dialog-prompts.md` (тон, утечки имён файлов, утечки slash-команд, объяснение терминов). Каждое нарушение → `finding`.

### Фаза 2: Wiring check

#### 2.1 AGENTS.md клиента
```bash
grep -q "$AGENT" "$CLIENT_OFFICE/office/AGENTS.md" \
  || echo "BLOCKER: агент не упомянут в AGENTS.md"
```

#### 2.2 Director клиента знает когда звать
```bash
DIRECTOR_FILE="$CLIENT_OFFICE/office/agents/director/core.md"
[ -f "$DIRECTOR_FILE" ] || DIRECTOR_FILE="$CLIENT_OFFICE/CLAUDE.md"
grep -q "$AGENT" "$DIRECTOR_FILE" \
  || echo "BLOCKER: Director не знает триггеров для $AGENT"
```

#### 2.3 Пути в core.md разрешаются
```bash
# Извлечь упомянутые .md файлы (только относительные)
grep -oE '`[a-zA-Z0-9_./-]+\.md`' "$TARGET/core.md" | tr -d '`' | sort -u | while read REL; do
  # Skip absolute or external paths
  case "$REL" in
    /*|http*) continue ;;
  esac
  # Try resolving relative to TARGET first, then CLIENT_OFFICE root
  if [ ! -e "$TARGET/$REL" ] && [ ! -e "$CLIENT_OFFICE/$REL" ]; then
    echo "MISSING: $REL"
  fi
done
```

#### 2.4 File ownership conflicts
Если у клиента есть `knowledge/file-ownership.md` — прочитать список и сравнить с тем куда пишет новый агент (Input Contract в его `core.md` обычно содержит секцию «Файлы владения»).

#### 2.5 Skills wiring
```bash
# В клиентском шаблоне скиллы агента могут жить в .claude/skills/$AGENT-*/
ls "$CLIENT_OFFICE/.claude/skills/" 2>/dev/null | grep "^$AGENT" \
  || ls "$TARGET/skills/" 2>/dev/null \
  || echo "MEDIUM: скиллы агента не найдены ни в .claude/skills/ ни в $TARGET/skills/"
```

#### 2.6 Knowledge файлы
```bash
# Все knowledge/*.md упомянутые в core.md — существуют?
grep -oE 'knowledge/[a-zA-Z0-9_./-]+\.md' "$TARGET/core.md" | sort -u | while read REL; do
  if [ ! -e "$TARGET/$REL" ] && [ ! -e "$CLIENT_OFFICE/$REL" ]; then
    echo "MEDIUM knowledge missing: $REL"
  fi
done
```

#### 2.7 КРИТИЧНО — утечка данных другого клиента

**Самое опасное место.** Если в `failures.md`/`memory.md`/`agent-state.md` агента остались записи про **других клиентов** — клиент увидит чужие данные.

Подход: собрать список **возможных имён клиентов** из исходного офиса пользователя (`<исходный-офис>/clients/INDEX.md` или `<исходный-офис>/office/hub/clients/INDEX.md` — путь зависит от того, как устроен твой офис), потом грепнуть их по файлам памяти агента в целевом офисе.

```bash
# Собрать список slug'ов клиентов из имён папок в мастер-офисе.
# Папки лучше заголовков таблицы — в них имена реальных клиентов, не технические слова.
NAMES_FILE="$(mktemp)"
for DIR in "$HOME/workspace/clients" "$HOME/workspace/office/hub/clients"; do
  [ -d "$DIR" ] && ls -1 "$DIR" 2>/dev/null \
    | grep -vE '^(_|\.|INDEX|README|TEMPLATE)' \
    | grep -oE '^[a-zа-яё][a-zа-яё0-9-]+' \
    | awk 'length($0) >= 4' >> "$NAMES_FILE"
done
sort -u "$NAMES_FILE" -o "$NAMES_FILE"

if [ ! -s "$NAMES_FILE" ]; then
  echo "TODO: список клиентов из мастер-офиса не собран. Проверь файлы памяти агента вручную перед передачей клиенту."
else
  # Грепнуть по файлам памяти агента — ищем имена целиком (с word boundary)
  for FILE in "$TARGET/failures.md" "$TARGET/memory.md" "$TARGET/agent-state.md" "$TARGET/agent-state-template.md"; do
    [ -f "$FILE" ] || continue
    while IFS= read -r NAME; do
      [ -z "$NAME" ] && continue
      # \b не работает для кириллицы в BSD grep — используем grep -wiF
      if grep -wiF "$NAME" "$FILE" >/dev/null 2>&1; then
        echo "BLOCKER LEAK: $(basename $FILE) содержит '$NAME' (slug другого клиента)"
      fi
    done < "$NAMES_FILE"
  done
fi
rm -f "$NAMES_FILE"
```

⚠️ **Важно:** ловим **slug'и папок** (`tatyana-lawyer`, `vitaly`), а не **отдельные слова** из таблицы INDEX.md (типа «Дата», «Статус», «Клиент»). Это убирает ложные срабатывания. Если у тебя клиенты названы только русскими именами без slug'а — добавь grep по этим именам отдельно.

**Если SOURCE_CLIENTS пуст** (нет доступа к мастер-INDEX) — Демиург в отчёте явно говорит: «не смог сверить с базой клиентов — проверь файлы памяти агента вручную перед передачей клиенту». **Это не PASS, это TODO для пользователя.**

### Фаза 4: Apply approved patches

Куда писать — определяется классификатором каждой находки (см. начало SKILL.md).

#### 4.1a SYSTEM-BUG → core.md мастер-пака

Для находок с тегом `SYSTEM-BUG`:
- Фикс идёт в **`core.md` мастер-пака** (или соответствующий SKILL.md / agent-state-template.md)
- После применения — **не объявлять готовым**, а вывести список требуемых действий пользователю:
  ```
  ⚠ SYSTEM-BUG правки применены к мастер-паку. Требуется:
    1. Просмотреть diff: git diff <файлы>
    2. Бамп версии в README.md / install.md (например v2.0 → v2.1)
    3. Дописать CHANGELOG (что изменено, почему)
    4. git commit + push в публичный репо
    5. Уведомить учеников чтобы запустили /update-office
  ```
- Скилл сам **не делает** push, commit, bump версии — это решение пользователя

#### 4.1b CLIENT-SPECIFIC → overrides.md агента

Для находок с тегом `CLIENT-SPECIFIC` — идут в **`$TARGET/overrides.md`** в раздел `## Адаптация (auto)`. Если файла нет — создаём из шаблона:

```markdown
# <Agent name> — Client Overrides

Эти правила имеют приоритет над `core.md` и `soul.md`. Файл НЕ трогается при апдейте ядра.

## Адаптация под клиентский офис (auto)

### Pre-flight evidence — internal-only
Pre-flight (чтение agent-state.md, memory.md, failures.md) выполняй **молча**.
Не выводи строку «📚 Прочитал память: N записей...» клиенту. Pre-flight = audit
trail в логах, не реплика.

### Маршрутизация к скиллам — без озвучки имён
При запуске скиллов внутри своей работы — не произноси slash-команды клиенту.
Запускай молча, в реплике используй живой язык:
- «давай распакуем твою аудиторию» (вместо «/audience-stage»)
- «давай разберём сегменты» (вместо «/segments-discover»)

### Англицизмы — переводи при первом упоминании
- scoring → оценка 1-5
- multi-perspective → с разных углов
- confidence → уверенность

### Пути под клиентскую структуру
- client-profile → читать из `office/client-profile.md` (не `../../`)
```

После применения — добавить footer:
```
<!-- last-adapted: 2026-04-28T15:44+03:00 -->
<!-- applied-findings: 1, 2, 3, 5 -->
```

#### 4.2 Wiring-правки → точечные правки соответствующих файлов

Wiring **не идёт через overrides.md** — это структурные изменения в файлах клиентского офиса (AGENTS.md, Director core.md). Применяются точечно через Edit:

- `AGENTS.md` — добавить строку в таблицу команды
- Director `core.md` — добавить триггер маршрутизации
- Утечки данных в `failures.md`/`memory.md` — обнулить эти файлы до пустых шаблонов

  grep -q "errors" /tmp/adapt-validate.log && echo "POST-VALIDATE FAILED — НЕ объявлять готовым"

## Критерий успеха

Пользователь открывает клиентский офис, пишет агенту / Director подхватывает, диалог идёт. Видит:

1. ✅ Живое нормальное приветствие (без «📚 Прочитал память: N записей»)
2. ✅ Понятный диалог без техжаргона, имён файлов, slash-команд вслух
3. ✅ Чистый роутинг — Director клиента подхватывает темы и зовёт нужного агента
4. ✅ Агент ссылается на офисные данные клиента корректно (правильные пути)

**Цитата владельца дословно:** «когда увижу что диалог живой, понятный, агент хорошо поприветствовал, нет ничего загружающего, и всё чётенько роутится».

При апдейте мастер-пака `core.md` обновится, **`overrides.md` останется** — повторять адаптацию не нужно (только если в новой версии core.md появились новые жаргонные паттерны).

## Self-trigger rules

| Если | То |
|------|-----|
| Запускается без аргументов | Спросить у пользователя «какого агента и в чей офис?» одной фразой |

| Конфликт с `/office-cleaner (Рита)` (пересекающиеся проверки routing/structure) | Этот скилл — про **per-agent адаптацию**. Если пользователь хочет общий аудит офиса — направить на `/office-cleaner (Рита)`. |
| 2 фейла подряд при попытке применить правки | STOP. Не пиши correctional prompts. Эскалируй: «две попытки не сработали, подхожу иначе» |
