# Wiring checklist — что и где проверять

Что должно быть подключено правильно, чтобы новый агент **жил** в клиентском офисе, а не просто лежал файлом.

---

## 1. AGENTS.md клиента — карточка агента

**Где:** `office/AGENTS.md` (или корневой `AGENTS.md` если структура плоская)

**Что должно быть:**
- Строка с именем агента
- Краткое описание роли (1 предложение, на языке клиента — без жаргона)
- Когда звать (триггеры)
- Путь до агента

**Пример хорошей строки:**
```markdown
| **Алекс** | Маркетолог-навигатор. Помогает понять кому продавать и где деньги | «не понимаю кому продаю», «найди мою аудиторию», «разберём покупателей» | `office/agents/alex-marketer/` |
```

⚠️ В триггерах не используй методологические термины («распакуй ЦА», «сегменты», «JTBD») — это жаргон. Триггер должен звучать как живая жалоба клиента, а не как команда из учебника.

**Severity нарушений:**
- Агент отсутствует в AGENTS.md → BLOCKER (Director не узнает о нём)
- Описание содержит технические термины → MEDIUM
- Триггеры пустые или дублируют другого агента → MEDIUM

---

## 2. Director клиента — триггеры маршрутизации

**Где:** `office/CLAUDE.md` или `office/agents/director/core.md` (или корневой `CLAUDE.md` если у клиента нет отдельного Director'а)

**Что должно быть:**
- Раздел «когда звать [имя агента]» с конкретными триггерами
- Tier классификация если она используется в этом офисе
- Связи с другими агентами (handoff)

**Пример хорошей записи:**
```markdown
## Когда звать Алекса
- Любой вопрос про ЦА, сегменты, покупателей
- «не знаю кому продавать», «непонятная аудитория»
- Перед оффером (распаковка ЦА = блокер для оффера)
Tier: 1 (revenue-критично)
```

**Severity нарушений:**
- Director не знает агента → BLOCKER (агент будет неактивен, никто не позовёт)
- Триггеры пересекаются с другим агентом без приоритета → MEDIUM
- Tier не указан, но в этом офисе все агенты с Tier → COSMETIC

---

## 3. Пути в core.md агента

**Что проверять:**
Все относительные пути в `core.md` нового агента — разрешаются ли в реальной структуре клиентского офиса?

**Типичные проблемы:**
- В исходном офисе `clients/`, у клиента `customers/` или наоборот
- В исходном `../../client-profile.md`, у клиента `../client-profile.md` (структура папок отличается на уровень)
- Knowledge файлы упомянутые в core.md не переехали в клиентский офис
- Symlinks в исходном офисе — у клиента физических папок нет

**Команда сверки:**
```bash
# Извлечь все упомянутые .md файлы в core.md
grep -oE '`[a-zA-Z0-9_/.-]+\.md`' {agent}/core.md | sort -u | while read f; do
  path=$(echo "$f" | tr -d '`')
  # Резолвить относительно core.md
  full="{client_office}/{agent_dir}/$path"
  [ -e "$full" ] && [ -e "{client_office}/$path" ] || echo "MISSING: $path"
done
```

**Severity:** если упомянутый путь не существует → BLOCKER (агент будет писать «File not found» при работе)

## 4. File ownership — конфликты

**Где смотреть:**
- `knowledge/file-ownership.md` (если у клиента есть)
- Списки файлов которые агент **пишет напрямую** (упомянуты в его `core.md` секцией Input Contract / Files)

**Что искать:**
Файлы которые новый агент пишет — не пишет ли в них уже другой агент клиента? Если да → конфликт.

**Severity:**
- Прямое пересечение (двое пишут в один файл без координации) → BLOCKER
- Пересечение с координацией через diff/log → COSMETIC (так и задумано)
- Пересечение в read-only файлы → COSMETIC

---

## 5. Skills wiring

**Что проверить:**
- Все привязанные `skills/{name}/SKILL.md` физически в клиентском офисе?
- В description (фронтматтер) каждого SKILL.md — нет ли ссылок на отсутствующие у клиента вещи?
- Скилл не вызывает другие скиллы которых у клиента нет?

**Команда:**
```bash
ls {client_office}/agents/{agent}/skills/ 2>/dev/null
# Каждый SKILL.md — проверить description на ссылки
```

**Severity:**
- Скилл упомянут в core.md, но физически отсутствует → BLOCKER
- Скилл вызывает другой скилл которого нет → BLOCKER
- Скилл ссылается на knowledge файл которого нет → MEDIUM

---

## 6. Knowledge ссылки

**Что проверить:**
- Все `knowledge/*.md` файлы упомянутые в `core.md`, `soul.md`, SKILL.md — физически на месте?
- `knowledge/INDEX.md` существует и актуален?
- Внутренние ссылки внутри knowledge файлов — резолвятся?

**Команда:**
```bash
grep -rE 'knowledge/[a-zA-Z0-9_/.-]+\.md' {client_office}/agents/{agent}/ | while read line; do
  # вытащить путь, проверить существование
  ...
done
```

**Severity:** missing → MEDIUM (агент будет ссылаться на несуществующее, но не упадёт)

---

## 7. agent-state.md / memory.md / failures.md

**Что проверить:**
- Эти файлы переехали? Если в исходном офисе они были с историей — у клиента они должны быть **пустые шаблоны**, не история твоей работы
- Опасно: если переехала твоя `failures.md` с записями про твоих клиентов → клиент увидит чужие данные!

**Severity:** утечка данных другого клиента → BLOCKER + Critical (требует немедленной правки)

---

## 8. Optional — wire-check.sh

Если в `demiurg/scripts/wire-check.sh` есть автоматическая проверка — прогнать её на адаптированном агенте:

```bash
bash demiurg/scripts/wire-check.sh {client_office}/office/agents/{agent} 2>&1
```

Любые errors из скрипта → добавить в findings с severity по тяжести (errors → BLOCKER, warnings → MEDIUM).
